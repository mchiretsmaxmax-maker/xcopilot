# AI co-pilot для X — разбор архитектуры и план разработки (v3)

> База: `architecture-v2.md`. Факты о внешних сервисах (X API, DeepSeek, Jev, Claude, версии библиотек) сверены 12.11.2026, источники — в конце.
>
> Структура: **Часть 0** (= «Этап 0» из запроса) — критика, предложения, обновлённая архитектура. **Часть 1** (= «Этап 1») — план разработки: 21 этап, каждый — отдельная ветка, тесты раньше кода. В конце — полный список допущений.

## Главные развороты (коротко)

1. **Ответы через API X закрыты.** Отвечать может только человек. Бот готовит текст и даёт ссылку, которая открывает X с готовым ответом.
2. **Jev не пишет текст.** Он возвращает типизированные оценки с вероятностями. Инструкции для переписывания собирает код из этих оценок.
3. **DeepSeek не даёт эмбеддингов.** Эмбеддинги локальные. Сбор данных и поиск — код, а не модель.
4. **БД — PostgreSQL + pgvector с первого дня.** Тенант в каждой таблице, журнал событий, каталог метрик, автоспецификация. SQLite, Chroma и файлы как источник правды убраны.
5. **«12 агентов» → один конвейер из шагов с контрактами.** Фазы нарезаны по пользе для владельца, а не по числу агентов.
6. **MVP работает без платного чтения чужих постов.** Платный X включается отдельным режимом с дневным лимитом в деньгах.

# ЧАСТЬ 0. КРИТИКА И ОБНОВЛЁННАЯ АРХИТЕКТУРА

## 0.1 Критика: слабые места v2

### A. Уязвимо, рискованно или нереализуемо

| # | Что не так | Почему это проблема |
|---|---|---|
| K1 | **Ответы через API.** В v2 «Снайпер» и ответы — штатная функция | С 23.02.2026 X отклоняет программные ответы (`POST /2/tweets` с `in_reply_to`), если автор исходного поста сам не упомянул или не процитировал аккаунт. Действует на всех self-serve тарифах. Ценность Снайпера сводится к скорости подготовки текста |
| K2 | **Стоимость X API не учтена** | Подписок нет, оплата за каждый ресурс: чужой пост $0.005, профиль $0.010, свои данные $0.001, тренды $0.010 за запрос. В v2 нет ни бюджета, ни режимов. Наблюдатель, конкуренты и Снайпер — расход без потолка |
| K3 | **Jev — не LLM** | Он отвечает на типизированные вопросы (да/нет, выбор, шкала) и не генерирует текст. Петля «Jev №2 не одобрил → Claude переписывает» не замкнута: некому сказать, что править. Плюс ранний доступ и неопубликованные лимиты, а на нём двое ворот |
| K4 | **Эмбеддинги у DeepSeek** | В API DeepSeek эмбеддингов нет. «DeepSeek владеет вектор-базой» невыполнимо. «Сбор данных» — работа кода (HTTP, расписание), а не модели |
| K5 | **Вредные fallback'и** | «Claude упал → пишет DeepSeek» засоряет базу стиля чужим голосом. «Jev упал → оценивает Claude» — автор проверяет сам себя. oEmbed отдаёт один пост по ссылке, без метрик, длинные посты режет |
| K6 | **Петля переписывания без предела** | Бесконечный цикл и неконтролируемый расход |
| K7 | **«AI-запах» проверяет только модель** | Нестабильно, не воспроизводится, стоит денег. Нет дешёвых детерминированных проверок |
| K8 | **Недоверенный контент в промптах** | Чужие посты, PDF и переписки идут в модель без изоляции (prompt injection). В переписках чужие персональные данные, они уходят трём внешним провайдерам |
| K9 | **«Самообучение» не определено** | Неясно, что меняется после правки, кто это подтверждает, как откатить и чем доказать, что стало лучше |
| K10 | **Факты и цифры без владельца** | В v2: «проверка цифр — код или Claude», но шага в конвейере нет. Выдуманная цифра в посте — главный репутационный риск |

## 0.3 Обновлённая архитектура

**Одна фраза:** Telegram-бот, который учится голосу аккаунта на примерах и правках, готовит посты и ответы, проверяет их кодом и судьёй, а публикует только человек.

### Конвейер

```
ВХОД
 ├─ ручной: текст · ссылка на пост · @аккаунт · файл            (MVP)
 └─ фоновый: Радар — конкуренты и X-список                      (фаза 2)
      │
      ▼
ИНГЕСТ (код) → чистка → теги (cheap) → эмбеддинг (локально) → PostgreSQL
      │
      ├─ только для потока: ВОРОТА №1 — релевантность (judge, пороги)
      ▼
КОНТЕКСТНЫЙ ПАКЕТ (код): паспорт + жёсткие правила + 8–12 примеров
                         + принятые уроки + факты с источниками
      ▼
ПИСАТЕЛЬ (writer) → 3 варианта
      ▼
ЛИНТЕР (код) ──ошибка──┐
      ▼                │
ВОРОТА №2 (judge) ──не прошёл──► инструкции из кодов замечаний → writer (≤ 2 раз)
      ▼
КАРТОЧКА в Telegram → Одобрить · Править · Ещё вариант · Отклонить
      ▼
ПУБЛИКУЕТ ЧЕЛОВЕК (ссылка Web Intent) → подтверждение или автосверка
      ▼
МЕТРИКИ своих постов (owned reads) → события → каталог метрик
      ▼
УРОКИ из правок и отказов → подтверждение владельца → новая версия паспорта
```

### Модели и роли

| Роль | Модель | ID в API | Что делает | Цена (на 12.11.2026) |
|---|---|---|---|---|
| `writer` | Claude Opus 5.5 | `claude-opus-5-5` | черновики, извлечение стиля, уроки из правок, тексты аналитики и плана | $4 / $20 за 1M токенов вход/выход; чтение кэша $0.20 |
| `judge` | Jev (TypeSafe) | `jev-latest`, при деплое закрепляется точная версия из `GET /v1/models` | ворота №1 и №2, ранжирование | около $0.042 за 1M входных токенов, выход бесплатный |
| `cheap` | DeepSeek V4.1 Flash | `deepseek-flash` | теги, нормализация, сводки, текст ежедневного отчёта, резервный судья | $0.15 / $0.60 вне пика, $0.30 / $1.20 в пик (01–04 и 06–10 UTC по будням) |
| эмбеддинги | локально, fastembed | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (384d) | векторы для поиска и дедупа | бесплатно |

Модель не «владеет» данными. Данными владеет БД, модели вызываются через шлюз по роли.

### Режимы доступа к X

| Режим | Что читаем | Цена | Когда |
|---|---|---|---|
| `off` | пост по ссылке через oEmbed (без ключей, длинные посты может обрезать — тогда бот просит текст) | $0 | старт без ключей |
| `owned` (по умолчанию в MVP) | свои посты и метрики через `GET /2/users/{id}/tweets` | $0.001 за пост; ежедневный синк 100 постов ≈ $3 в месяц | MVP |
| `paid` | чужие посты, ленты конкурентов, список | $0.005 за пост, $0.010 за профиль; дневной лимит обязателен | фаза 2, включается явно |

Запись в X не используется ни в одном режиме. Scope токена: `tweet.read users.read offline.access`.

### Что происходит при сбоях

| Сбой | Поведение |
|---|---|
| Claude | Генерация уходит в очередь с повтором, владелец получает уведомление. Готовые карточки работают. Другие модели текст не пишут |
| Jev | Резервный судья — DeepSeek Flash с той же схемой, карточка помечена «резервный судья». Оба недоступны → только линтер и пометка «без судьи» |
| DeepSeek | Теги и сводки откладываются. Ежедневный отчёт собирается шаблоном без модели |
| X API | Своя аналитика на паузе. Чтение по ссылке идёт через oEmbed. Если и он недоступен — бот просит прислать текст |
| PostgreSQL | Бот отвечает «техработы», уходит алерт. Задачи не теряются: очередь в БД, обработчики идемпотентны |
| Telegram | Отправка повторяется. Карточка получает статус «показана» только после успешной доставки |

## 0.4 Модель данных (усиленный блок)

Требование: БД на вырост, с удобной системой метрик и спецификацией, масштабируемая, под постоянное использование.

### Принципы

1. **Одна БД — PostgreSQL 18.** Расширения: `vector` (pgvector 0.8), `pg_trgm`. Выход PostgreSQL 19 намечен на 19.11.2026 — на него не закладываемся, переход после первого минорного релиза.
2. **Тенант везде.** В каждой бизнес-таблице `account_id NOT NULL`, все индексы начинаются с него. Глобальные данные (анти-AI правила) принадлежат системному аккаунту `kind = 'global'`, чтобы правило «`account_id` обязателен» не имело исключений.
3. **Ключи — UUIDv7** (`DEFAULT uuidv7()`, встроено в PG 18). Упорядочены по времени, не конфликтуют при слиянии и шардинге.
4. **Сырьё отдельно от выводов.** `sources / documents / chunks` неизменяемы. Выводы (`style_passports`, `lessons`, `insights`, `facts`) всегда ссылаются на источник.
5. **Журналы только на добавление и по месячным партициям:** `events`, `llm_calls`, `x_api_calls`, `post_metric_snapshots`. Старые партиции архивируются целиком.
6. **Версии вместо перезаписи:** паспорт стиля, промпты, определения метрик, ревизии черновиков.
7. **Метрики как данные:** `metric_definitions` (каталог) + `metric_values` (свёртки). Отчёты читают только свёртки и представления.
8. **Гибкие поля в JSONB** со схемой pydantic и `schema_version`. Всё, по чему фильтруем, — обычные колонки.
9. **Деньги — целые микродоллары** (`cost_micro_usd BIGINT`), время — `timestamptz` в UTC, пояс аккаунта в `accounts.tz`.
10. **Идемпотентность:** уникальные ключи на ингест (`content_hash`), задачи (`idempotency_key`), подтверждения публикаций.
11. **Миграции только через Alembic**, каждая обратима. Схема из моделей и из миграций обязана совпадать — это проверяет тест.
12. **Спецификация генерируется:** `COMMENT ON` для каждой таблицы и колонки → `docs/db/schema.md` + ER-диаграмма (Mermaid) + `docs/db/metrics.md`. CI падает, если файлы устарели.

### Система метрик

Три слоя:

1. **Факты** — `events` и `post_metric_snapshots`. Только добавление.
2. **Каталог** — `metric_definitions`. Одна метрика = один файл `metrics/definitions/<key>.sql` с шапкой (название, единица, зерно, измерения, версия) и запросом `SELECT period_start, dims, value, sample_size`. Формулы грузятся из репозитория, из интерфейса не редактируются и исполняются в транзакции `READ ONLY`.
3. **Свёртки** — `metric_values`. Ночная задача считает вчера по поясу аккаунта, «сегодня» считается на лету. Пересчёт идемпотентен, есть команда бэкфилла.

Ядро схемы:

```sql
CREATE TABLE events (
  id          uuid        NOT NULL DEFAULT uuidv7(),
  account_id  uuid        NOT NULL REFERENCES accounts(id),
  ts          timestamptz NOT NULL DEFAULT now(),
  type        text        NOT NULL,          -- 'review.approved', 'draft.generated', ...
  actor       text        NOT NULL,          -- user | system | model
  user_id     uuid,
  entity_type text,
  entity_id   uuid,
  props       jsonb       NOT NULL DEFAULT '{}',
  PRIMARY KEY (ts, id)
) PARTITION BY RANGE (ts);
CREATE INDEX ON events (account_id, type, ts);
CREATE INDEX ON events (account_id, entity_type, entity_id);

CREATE TABLE metric_values (
  account_id         uuid    NOT NULL REFERENCES accounts(id),
  metric_key         text    NOT NULL REFERENCES metric_definitions(key),
  grain              text    NOT NULL,            -- day | week
  period_start       date    NOT NULL,
  dims               jsonb   NOT NULL DEFAULT '{}',
  dims_hash          text    NOT NULL,
  value              numeric,
  sample_size        integer NOT NULL,
  definition_version integer NOT NULL,
  computed_at        timestamptz NOT NULL,
  PRIMARY KEY (account_id, metric_key, grain, period_start, dims_hash)
);
```

Пример определения (`metrics/definitions/zero_edit_rate.sql`):

```sql
-- key: zero_edit_rate
-- title: Доля черновиков, одобренных без правок
-- unit: ratio · grain: day · version: 1
SELECT (e.ts AT TIME ZONE :tz)::date AS period_start,
       '{}'::jsonb AS dims,
       count(*) FILTER (WHERE e.type = 'review.approved')::numeric
         / NULLIF(count(*), 0) AS value,
       count(*) AS sample_size
FROM events e
WHERE e.account_id = :account_id
  AND e.ts >= :from AND e.ts < :to
  AND e.type IN ('review.approved', 'review.edited', 'review.rejected')
GROUP BY 1;
```

**Стартовый каталог метрик**

| Ключ | Что показывает | Как считается |
|---|---|---|
| `zero_edit_rate` | бот пишет «как я» (главная метрика) | одобрено без правок / все решения |
| `approval_rate` | доля черновиков, дошедших до публикации | (одобрено + отредактировано) / все решения |
| `edit_distance_avg` | насколько сильно владелец правит | средняя нормированная дистанция «до/после» |
| `reject_rate_by_reason` | за что отклоняют | доля отказов по `reason_code` (измерение) |
| `judge_owner_agreement` | калибровка судьи | доля вердиктов судьи, совпавших с решением владельца |

### Путь роста

| Порог | Что делаем | Что уже заложено |
|---|---|---|
| до ~10 аккаунтов, ~1M кусков | один инстанс Postgres, HNSW, месячные партиции | всё из коробки |
| несколько человек на аккаунт, внешние клиенты | включаем RLS (этап 17), пул соединений, разделяем процессы бота и воркера | `account_id` везде, роли, очередь в БД |
| векторов больше ~5M или БД больше ~50 ГБ | `halfvec`, отдельный инстанс под эмбеддинги, реплика на чтение для аналитики | `embedding_models`, поиск за интерфейсом |
| событий больше ~100M | старые партиции в холодное хранилище (Parquet), свёртки остаются | партиции, `metric_values` |
| смена модели эмбеддингов | новая запись в `embedding_models`, фоновая переиндексация, переключение флагом | `model_id` в `embeddings` |
| задач больше ~50 в секунду | вынос очереди в отдельный брокер | очередь за интерфейсом `jobs.queue` |

## 0.6 Зафиксированные решения

Полный список допущений — в конце документа.

1. Хранилище — PostgreSQL 18 + pgvector + pg_trgm. SQLite, Chroma и sqlite-vec не используются.
2. `account_id` обязателен во всех бизнес-таблицах с первой миграции. RLS включается на этапе 17.
3. Роли моделей: `writer` = Claude Opus 5.5, `judge` = Jev, `cheap` = DeepSeek V4.1 Flash. Привязка в конфиге.
4. Эмбеддинги локальные: fastembed, `paraphrase-multilingual-MiniLM-L12-v2`, 384 измерения.
5. Бот никогда не пишет в X. В клиенте X нет методов записи, токен без scope `tweet.write`.
6. Публикация — ссылка Web Intent (`https://x.com/intent/tweet?text=…&in_reply_to=…`). Пост длиннее 280 знаков и треды выдаются блоками для копирования.
7. Режим X по умолчанию — `owned`. Режим `paid` включается владельцем после экрана с оценкой расхода.
8. Писатель не имеет замены. Резервный судья — DeepSeek Flash с той же схемой.
9. Петля переписывания — не больше 2 попыток (в Снайпере — 1).
10. Уроки влияют на генерацию только после подтверждения владельцем.
11. Жёсткие правила стиля (регистр, эмодзи, хэштеги, длина, стоп-фразы) определяются статистикой по примерам и проверяются кодом, а не моделью.
12. Любая цифра в черновике должна быть в фактах контекстного пакета или во входе владельца. Иначе линтер возвращает черновик.
13. Чужой контент попадает в промпты только в обёртке «недоверенные данные». В переписках и файлах e-mail и телефоны заменяются заглушками до сохранения.
14. Каждое действие пользователя и каждый шаг конвейера пишет событие в `events` в той же транзакции.
15. Метрика добавляется SQL-файлом в каталог. Отчёты не содержат собственных формул.
16. Очередь задач и расписания — в PostgreSQL. Отдельного брокера нет.
17. Один процесс приложения в MVP, один контейнер БД, деплой через Docker Compose.
18. Интерфейс бота на русском. Язык постов задаётся на аккаунт (`accounts.lang`).
19. Авторизация X — OAuth 2.0 PKCE с `offline.access`. Каждый аккаунт подключает свой developer app: так его чтения тарифицируются как owned, а ключи изолированы.
20. «Тренды рынка», X-статьи, auto-plug и публикация через API — вне плана.

# ЧАСТЬ 1. ПЛАН РАЗРАБОТКИ

## 1.0 Общие правила

### TDD — порядок работы в каждой ветке

1. Ветка создаётся от `main`: `stage/NN-имя`. Один этап = одна ветка = один PR.
2. **Первые коммиты — только тесты** из раздела «Тесты (до кода)» и пустые заглушки интерфейсов, чтобы тесты импортировались. CI обязан быть красным. Коммит помечается тегом `stage-NN-red`.
3. Дальше пишется код до зелёного. Исходные тесты менять нельзя. Если тест оказался неверным — отдельный коммит `test-fix:` с объяснением в PR, ревьюер подтверждает явно.
4. Скрипт `scripts/check_tdd.sh` в CI проверяет: тег `stage-NN-red` существует, ни один тест из него не удалён и не пропущен (`skip`, `xfail`).
5. **Этап закрыт, только если зелёные все исходные тесты** и выполнен общий критерий ниже.
6. Не прошли — merge запрещён. В PR заполняется таблица «Что чинить»: тест → причина падения → правка → кто делает.

### Общий критерий готовности (действует для каждого этапа)

1. Все исходные тесты этапа зелёные, тесты предыдущих этапов не сломаны.
2. Покрытие новых модулей — не ниже 85% строк.
3. `ruff check`, `ruff format --check`, `mypy --strict` — без ошибок.
4. Миграции накатываются с нуля и откатываются до нуля.
5. `docs/db/schema.md` и `docs/db/metrics.md` актуальны, если этап трогал схему или метрики.
6. Каждое новое действие пользователя и каждый новый шаг конвейера пишет событие в `events`.
7. Секреты не попадают в логи, журнал вызовов и тексты ошибок.

## Этап 3: Метрики-ядро  (ветка: stage/03-metrics-core)

- **Цель:** любое событие продукта пишется одной функцией, а любая метрика добавляется одним SQL-файлом и сразу доступна отчётам.
- **Задачи:**
  1) Перечень типов событий и схема `props` для каждого.
  2) `emit()` — запись события в текущей транзакции.
  3) Загрузчик каталога: разбор шапки и запроса из `definitions/*.sql`, синхронизация в `metric_definitions`, контроль версии по хэшу формулы.
  4) Движок свёрток: исполнение формулы в транзакции `READ ONLY`, запись в `metric_values` через upsert.
  5) Ночная задача свёртки по поясу аккаунта, расчёт «сегодня» на лету, команда бэкфилла.
  6) API чтения: ряд по периоду, одно значение, разрез по измерению.
  7) Представления `v_post_checkpoints`, `v_draft_funnel`.
  8) Стартовый каталог: 17 метрик из раздела 0.4, каждая с фикстурой.
  9) Генератор `docs/db/metrics.md`.
- **Код:**

## Этап 4: LLM-шлюз  (ветка: stage/04-llm-gateway)

- **Цель:** любой шаг вызывает модель по роли, получает проверенный типизированный ответ, а вызов учтён в журнале и в бюджете.
- **Задачи:**
  1) Конфиг ролей `config/models.toml` и цен `config/pricing.toml` (с датой сверки).
  2) Адаптеры: Anthropic (`writer`), DeepSeek через OpenAI-совместимый API (`cheap`), TypeSafe (`judge`).
  3) Типизированные ответы: JSON-схема из pydantic-модели, проверка, одна попытка починки с текстом ошибки.
  4) Единые типы вопросов и ответов судьи: `NoulQ`, `ChoiceQ` (до 255 вариантов), `ScoreQ` (до 10 уровней).
  5) Реестр промптов: файлы с шапкой → таблица `prompts`, версия по хэшу содержимого, старые версии не затираются.

  7) Расчёт стоимости: Claude с чтением и записью кэша; DeepSeek с пиковыми часами; Jev — только вход.
  8) Бюджет: проверка до вызова, запись после; мягкий порог 80% (событие `budget.warning` раз в день), жёсткий стоп (`BudgetExceeded`).
  9) Повторы на 429, 5xx и таймауты (до 3, с паузой и разбросом); без повтора на 4xx.
  10) Предохранитель на провайдера: размыкание после N ошибок подряд, пробный вызов после паузы.
  11) Политика замены: у `writer` замены нет; у `judge` — `cheap` с той же схемой и флагом `fallback`.
  12) Обёртка недоверенного контента и кэшируемые блоки промпта (паспорт, уроки).

- **Цель:** всё, что владелец присылает боту (текст, ссылка на пост, @аккаунт, файл), превращается в очищенные куски с тегами и эмбеддингами, без дублей.
- **Задачи:**

  2) Парсеры: текст; пост X (через `XService`); PDF; DOCX; TXT и MD; экспорт Telegram (`result.json`, только сообщения владельца).
  3) Ограничения: файл до 20 МБ, текст до 50 тыс. знаков; понятный отказ.
  4) Чистка: пробелы, служебные параметры ссылок.
  5) Вычистка персональных данных в переписках и файлах: e-mail, телефоны, номера карт → заглушки.

## Этап 9: Ретривал  (ветка: stage/09-retrieval)

## Этап 10: Писатель  (ветка: stage/10-writer)

## Этап 11: Ворота качества  (ветка: stage/11-quality-gate)

- **Цель:** до владельца доходят только черновики, прошедшие линтер и судью; непрошедшие переписываются не больше двух раз по конкретным замечаниям.
- **Задачи:**
  1) Движок линтера: правило = класс с id, уровнем (`error` / `warn`) и методом проверки.
  2) Правила v1: `length`, `casing`, `emoji`, `hashtags`, `links`, `banned_phrases` (аккаунт + глобальные), `ai_patterns` (набор шаблонов RU и EN: «не X, а Y», избыток тире, тройные перечисления, штампы-зачины), `number_grounding`, `mention_safety`, `duplicate_of_recent` (сходство со своими постами за 60 дней выше 0.85), `thread_structure`, `language`.
  3) Автоисправление простого (регистр, хэштеги) с пометкой `autofixed`.
  4) Состояние для судьи: черновик, краткий паспорт, жёсткие правила, 3 примера автора, факты.
  5) Вопросы ворот №2:
     - `voice_match` — шкала 0–3: чужой голос → неотличимо от примеров;
     - `ai_smell` — шкала 0–3: явный AI-текст → читается как человек;
     - `hook` — шкала 0–2: нет зацепки → сильная первая строка;
     - `on_topic` — да/нет: текст раскрывает заданную тему;
     - `grounded` — да/нет: все утверждения с цифрами подтверждаются фактами;
     - `risky` — да/нет: оскорбления, финансовые обещания, призывы, опасные для аккаунта;
     - `main_issue` — выбор: `none`, `voice`, `ai_phrases`, `vague`, `too_long`, `weak_hook`, `off_topic`, `unsupported_claim`.
  6) Политика решения по порогам из `config/thresholds.toml` (переопределяются на аккаунт): `pass`, `rewrite`, `needs_owner`. Стартовые пороги: `voice_match ≥ 2.0`, `ai_smell ≥ 2.0`, `on_topic ≥ 0.7`, `grounded ≥ 0.7`, `risky ≤ 0.3`. ## Этап 12: Карточки и публикация  (ветка: stage/12-cards-publish)

- **Цель:** владелец получает карточку, одним нажатием одобряет, правит или отклоняет, публикует сам по ссылке, а система знает, какой черновик стал каким постом.
- **Задачи:**
  1) Отрисовка карточки: текст, счётчик длины, тема, строка проверки, кнопки; экранирование разметки; разбиение длиннее 4096 знаков.
  2) Схема callback-данных (до 64 байт, с версией) и проверка, что нажал участник аккаунта.
  3) Навигация по вариантам ◀ 1/3 ▶ редактированием одного сообщения.
  4) «Одобрить» → блок публикации: [🚀 Открыть в X] (ссылка Intent), [📋 Скопировать], [✔️ Опубликовал].
  5) «Править» → бот ждёт исправленный текст → сохраняет пару «до/после» и дистанцию → прогоняет линтер (ошибки показываются как предупреждения, владелец вправе оставить) → блок публикации.
  6) «Ещё вариант» → подсказки [Короче] [Жёстче] [Другой заход] или свой текст → новая генерация.
  7) «Отклонить» → причина: [Не мой голос] [Тема мимо] [Звучит как AI] [Факт неверный] [Другое].
  8) Идемпотентность нажатий; карточки старше 48 часов — `expired`, кнопки отключены.
  9) Подтверждение публикации: по ссылке от владельца или автосверкой со своей лентой (сходство текста от 0.85 в течение 48 часов; от 0.6 до 0.85 — вопрос владельцу; нет совпадения — `unconfirmed`).

## Этап 16: Радар  (ветка: stage/16-radar)

- **Цель:** бот по расписанию читает конкурентов и X-список в рамках дневного бюджета, отсекает шум воротами №1 и приносит кандидатов на ответ или цитату с готовыми черновиками.
- **Задачи:**
  1) Наблюдатели: ленты конкурентов и список X; курсор `since_id` на каждый источник.
  2) Планировщик бюджета: дневной лимит → максимум постов → интервалы опроса по приоритетам источников.
  3) Режим `paid` включается только после экрана согласия с оценкой расхода.
  4) Все прочитанные посты сохраняются и индексируются (за них уже заплачено); дедуп поста, пришедшего из двух источников.
  5) Ворота №1 (Jev): `relevance` — шкала 0–3; `reply_worthy` — да/нет; `kind` — выбор (`news`, `opinion`, `alpha`, `meme`, `question`, `promo`, `spam`); `risky` — да/нет. Состояние: пост (как недоверенные данные), ниша, краткий паспорт.
  6) Пороги и предел кандидатов в день; неуверенные идут в дайджест, а не в карточки.
  7) Кандидат → черновики ответа или цитаты через писателя и ворота №2 → карточка с [Открыть ответ в X].
  8) Срок жизни кандидата на ответ — 6 часов; тихие часы.
  9) Недельный дайджест конкурентов для аналитика.
  10) Расход Радара в ежедневном отчёте.
- **Код:**
  - `radar/watchers.py` — `poll_competitor(competitor_id)`, `poll_list(list_id)`.
  - `radar/budget_plan.py` — `plan(daily_limit, sources) -> list[PollSlot]`.
  - `radar/gate1.py` — `QUESTIONS_GATE1`, `score(post, account) -> Gate1Verdict`, `decide(verdict, thresholds) -> Gate1Decision`.
  - `radar/candidates.py` — `select_top(account_id, day, n)`, `expire_old()`.
  - `radar/digest.py` — `weekly_digest(account_id) -> Digest`.
  - `x/api_v2.py` — `get_user_posts(user_id, since_id)`, `get_list_posts(list_id, since_id)`.
  - `bot/routers/radar.py`; задачи `radar.poll`, `radar.gate`, `radar.expire`.
  - Миграция: таблицы `watch_lists`, `radar_candidates`.
- **Технологии:** X API v2 в режиме `paid` ($0.005 за пост), роль `judge`, очередь и расписания.
- **Soft:** «📡 Радар» → [Конкуренты] [X-список] [Лимит в день] [Тихие часы]. Экран согласия: «20 аккаунтов × ~10 постов в день ≈ 200 чтений ≈ $1 в день. Включить?» Карточка ответа: исходный пост цитатой, три варианта ответа, [🚀 Открыть ответ в X].

## Этап 17: Мульти-аккаунт  (ветка: stage/17-multi-account)

- **Цель:** один бот ведёт несколько аккаунтов с изоляцией данных, ключей, бюджета и голоса; у аккаунта может быть несколько участников с ролями.
- **Задачи:**
  1) Переключатель аккаунта `/account`; имя аккаунта в заголовке каждой карточки и отчёта.
  2) Создание второго и следующих аккаунтов через тот же онбординг; архивирование.
  3) Участники и роли: owner — всё; editor — карточки, правки, обучение; viewer — отчёты. Приглашение одноразовым кодом со сроком.
  4) RLS на всех таблицах с `account_id`: политика по `current_setting('app.account_id')`; приложение работает под ролью без `BYPASSRLS`; сессия выставляет `SET LOCAL app.account_id`.

  6) Глобальный слой: уроки системного аккаунта видны всем; перенос урока в глобальные — только администратором.
  7) Запрет на попадание чужих примеров голоса в пакет — проверяется на уровне БД и тестом.
  8) Маршрутизация уведомлений по ролям.
  9) Фоновые задачи исполняются в контексте своего аккаунта и его пояса.

## Этап 19: Снайпер  (ветка: stage/19-sniper)

- **Цель:** в заданные часы бот замечает пост из короткого списка, который разгоняется быстрее обычного, и не позже чем через 3 минуты приносит готовый ответ для ручной отправки — в пределах отдельного жёсткого бюджета.
- **Задачи:**
  1) Короткий список наблюдения (до 30 аккаунтов) и окна активности по часам.
  2) Частый опрос в окне (каждые 5 минут) поверх наблюдателей Радара.
  3) Скорость: прирост (лайки + репосты + ответы) за минуту между двумя наблюдениями.
  4) Базовая скорость автора: медиана по его последним 20 постам в том же возрасте.
  5) Вспышка: скорость не ниже `k ×` базовой и выше абсолютного минимума; первое наблюдение вспышкой не считается.
  6) Учёт стоимости: повторное чтение того же поста в те же UTC-сутки X не тарифицирует; журнал считает уникальные посты в сутки. Это «мягкая гарантия» X, поэтому свой жёсткий лимит `sniper` обязателен.
  7) Быстрый путь: без шага темы, два варианта ответа, линтер и судья, не больше одного переписывания.
  8) Срочное уведомление; карточка живёт 30 минут; пауза на автора после срабатывания.
  9) Замер времени «обнаружение → карточка» по событиям.
  10) Отправка ответа — только вручную по ссылке.
- **Код:**
  - `sniper/velocity.py` — `velocity(prev, cur) -> float`, `author_baseline(author_id, age_minutes) -> float`.
  - `sniper/detector.py` — `SpikeConfig`, `detect(observations) -> list[Spike]`.
  - `sniper/fast_path.py` — `handle_spike(spike) -> Draft`.
  - `sniper/windows.py` — `is_active(account_id, now) -> bool`.
  - Миграция: `sniper_watch`, `post_observations`; `bot/routers/sniper.py`; задачи `sniper.poll`, `sniper.handle`.
- **Технологии:** X API v2 `paid`, роли `writer` и `judge`, бюджет со scope `sniper`.
- **Soft:** «⚡ Вспышка: @author, 12 минут, скорость ×6 от обычной» + исходный пост + два варианта ответа + [🚀 Открыть ответ в X]. Настройки: список, окна, лимит в день, чувствительность. Оценка на экране включения: «30 аккаунтов × ~15 постов в день ≈ 450 чтений ≈ $2.25 в день».
- **Тесты (до кода):**
  - `test_velocity_computation`.
  - `test_author_baseline_from_history`.
  - `test_spike_requires_ratio_and_absolute_minimum`.
  - `test_no_spike_on_first_observation`.
  - `test_no_spike_for_author_without_history` — используется общий порог.
  - `test_sniper_only_in_active_windows`.
  - `test_sniper_budget_separate_and_hard`.
  - `test_repoll_same_post_same_utc_day_counted_once`.
  - `test_fast_path_max_one_rewrite`.

  - `test_card_expires_after_30_min`.

  - `test_sniper_events_allow_sla_metric`.
- **Критерий готовности:** неделя работы в двух окнах по 2 часа: лимит не превышен, медиана «обнаружение → карточка» ниже 3 минут, владелец отправил хотя бы один ответ из карточки; общий критерий выполнен.
- **Зависимости:** после этапа 16. Параллельно с этапом 18.

## Этап 20: Авто-коррекция и A/B  (ветка: stage/20-autotune-ab)

- **Цель:** пороги судьи, веса уроков и выбор форматов подстраиваются по накопленным данным, а гипотезы проверяются экспериментом.
- **Задачи:**
  1) Калибровка порогов ворот №2 по решениям владельца: подбор порогов с максимальным согласием; минимум 100 решений.
  2) Изменение порогов предлагается владельцу и применяется после подтверждения.
  3) Веса уроков по измеренному эффекту.
  4) Выбор формата и времени: Thompson sampling по вовлечённости против базового уровня; влияет на предложение тем.
  5) A/B: эксперимент = гипотеза + варианты (версии промпта, паспорта, тип зачина) + метрика из каталога + минимальная выборка.
  6) Назначение варианта детерминировано по id запуска.
  7) Вердикт только после набора выборки; отчёт с интервалом.
  8) Защита: жёсткие правила автоматически не меняются; каждое авто-изменение — событие и обратимо.
- **Код:**
  - `autotune/calibration.py` — `fit_thresholds(decisions) -> Thresholds`, `propose(account_id) -> Proposal | None`.
  - `autotune/bandit.py` — `Arm`, `choose(arms, rng) -> Arm`, `update(arm, reward)`.
  - `autotune/lesson_weights.py` — `reweigh(account_id)`.
  - `ab/experiments.py` — `create()`, `assign(run_id, experiment) -> str`, `evaluate(experiment_id) -> AbResult`.
  - Миграция: `ab_experiments`, `ab_assignments`, `threshold_history`; `bot/routers/experiments.py`.
- **Технологии:** стандартная библиотека (`statistics`, `random` с фиксируемым зерном), каталог метрик.
- **Soft:** «Судья расходится с тобой в 28% случаев. Если поднять порог голоса с 2.0 до 2.3, расхождение упадёт до 17%. Применить?» — [Да] [Нет]. «🧪 Эксперименты»: список, статус, результат с интервалом.

- **Критерий готовности:** на 20 контрольных вопросах владельца каждый ответ либо содержит ссылки на источники, либо честный отказ; общий критерий выполнен.
- **Зависимости:** после этапа 17. Параллельно с этапом 20.

## Вне плана

| Что | Почему |
|---|---|
| Публикация через API | Ответы закрыты правилами X; для обычных постов ссылка Intent даёт то же самое без прав записи и без $0.015–$0.20 за пост |
| Тренды рынка (цены, тикеры, нарративы) | Источник не определён. Вернуться после этапа 18 как к поставщику `facts` |
| X-статьи, auto-plug | Низкая ценность и риск — как в v2 |
| Дообучение моделей (fine-tuning) | Память, уроки и паспорт дают тот же эффект дешевле и обратимо |
| Работа через браузер, лайки, фолловинг | Запрещено ТЗ |

## Главные риски

| Риск | Что делаем |
|---|---|
| X снова меняет цены или правила | Цены в `config/pricing.toml`, режимы и жёсткие лимиты; запись в X не используется вовсе |
| Jev в раннем доступе: недоступен или меняет API | Адаптер за интерфейсом, кассеты контракта, резервный судья, режим «только линтер» |
| Голос не получается, владелец правит всё | `zero_edit_rate` с первого дня, уроки с подтверждением, eval-набор, порог регрессии |
| Расход растёт незаметно | Журнал каждого вызова, дневные жёсткие лимиты, алерт на 80% |
| Утечка ключей или чужой доступ | Шифрование токенов, белый список, БД без внешних портов, права 600 |
| Выдуманные факты в посте | `number_grounding`, вопрос `grounded` судье, публикует только человек |

## Полный список допущений

**Продукт**

1. MVP запускается на одном X-аккаунте с одним владельцем; схема и код уже рассчитаны на несколько.
2. Интерфейс бота — русский; язык постов задаётся на аккаунт (русский или английский).
3. «Публикует только человек» означает, что кнопку Post в X всегда нажимает человек. Бот не имеет прав записи.
4. «Специка» в требовании к БД прочитана как спецификация: словарь данных, ER-диаграмма и каталог метрик, которые генерируются из схемы.
5. Три шага старта из v2 сохранены; добавлен вопрос о языке постов.
6. Владелец готов подтверждать уроки и активировать версии паспорта вручную.
7. Причины отказа фиксированы пятью кнопками; свободный комментарий необязателен.

**Модели**

8. Доступ к API Anthropic, DeepSeek и TypeSafe есть, ключи выдаются команде.
9. `writer` = Claude Opus 5.5 (`claude-opus-5-5`), `cheap` = DeepSeek V4.1 Flash (`deepseek-flash`), `judge` = Jev (`jev-latest`, закрепляется конкретная версия).
10. Лимиты Jev на размер состояния и частоту запросов не опубликованы. Принято: состояние до 4000 токенов, до 10 вопросов в запросе; проверяется live-тестом на этапе 4, при отказе состояние сокращается.
11. Цена Jev (около $0.042 за 1M входных токенов) взята из публикаций, а не из официального прайса; на бюджет не влияет даже при ошибке в 10 раз.
12. Оценка расхода моделей: около $0.09 на генерацию трёх вариантов, порядка $30–50 в месяц на аккаунт при 10 генерациях в день. Это расчёт, а не замер; уточняется на этапе 10.
13. Локальной модели эмбеддингов (384 измерения) хватает для коротких постов на русском и английском; проверяется тестом на межъязыковое сходство.
14. Оценка токенов для бюджета контекста приблизительная (по длине текста), с запасом.

**X**

15. Цены и правила X API — по состоянию на 12.11.2026: $0.005 за чужой пост, $0.001 за свой, $0.010 за профиль, программные ответы закрыты.
16. У каждого аккаунта свой developer app, владелец которого — сам аккаунт. Тогда чтение своей ленты тарифицируется как owned.
17. OAuth 2.0 PKCE проходит без веб-сервера: адрес возврата локальный, владелец вставляет его в бота. Если X запретит такой адрес возврата, добавляется минимальная страница приёма кода (плюс один небольшой этап).
18. Суточная дедупликация тарификации в X — «мягкая гарантия». Бюджеты считаются так, будто она может не сработать.
19. oEmbed остаётся бесплатным и без авторизации; длинные посты может обрезать — тогда бот просит текст.
20. Web Intent принимает `text` до 280 знаков и `in_reply_to`; длинные посты и треды публикуются копированием.
21. Метрики постов доступны через `GET /2/users/{id}/tweets` с полями `public_metrics` и `non_public_metrics`; непубличные — только для постов не старше 30 дней.
22. Режим `paid` и Радар включаются только явным решением владельца; до этого чужие посты приходят вручную или по ссылке.

**Данные и инфраструктура**

23. PostgreSQL 18 с pgvector 0.8, образ `pgvector/pgvector:pg18` (наличие тега проверяется на этапе 1); переход на PostgreSQL 19 — после его первого минорного релиза.
24. Один сервер Ubuntu 24.04 с Docker Compose: от 2 vCPU, 4 ГБ памяти, 20 ГБ диска. Сервис ставится на хост со свободным CPU и диском, а не на уже перегруженный.
25. Бот работает через long polling; входящих портов нет.
26. Бэкап — ежедневный `pg_dump`, шифрование, копия на другой хост; допустимая потеря — сутки.
27. Файлы до 20 МБ (предел скачивания в Telegram Bot API); сканы без текстового слоя не распознаются.
28. Переписки и файлы уходят внешним провайдерам моделей после вычистки e-mail, телефонов и номеров карт; ответственность за право использовать эти материалы — на владельце.
29. Объёмы на горизонте года: до 10 аккаунтов, до 1 млн кусков, до 50 млн событий. Пороги следующего шага роста — в разделе 0.4.

**Процесс**

30. Команда работает через PR в `main`; CI — GitHub Actions; один этап = одна ветка = один PR.
31. Live-тесты и evals требуют настоящих ключей и запускаются вручную или ночью; обычный CI ходит только в PostgreSQL.
32. Эталонный eval-набор (30 тем и 30 постов) собирается из материалов владельца на этапе 15.
33. Версии библиотек — последние на PyPI на 12.11.2026; фиксируются в `uv.lock` и обновляются отдельными PR.
34. Размеры этапов (S / M / L) — относительная оценка сложности, а не сроки.
