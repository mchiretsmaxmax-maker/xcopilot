# ADR 0026 — Обучение на правках (этап 13)

Статус: принято (16.11.2026).

## Решения

1. **Модули.** `learning/diffing.py` (`EditSummary`, `classify_edit`), `learning/from_reviews.py` (`run`, `propose`, `detect_removed_devices`, `build_signals`), `learning/passport_sync.py` (`apply_confirmed_voice_item`), `learning/triggers.py` (`should_run`), `learning/effect.py` (`item_effect`, `Effect`), `learning/jobs.py` (`handle_learning_propose`). Запросы — `db/repos/learning.py` (`LearningRepo`). Модуля `lessons` из v3 нет. Миграции нет (номер 0010 не занят).
   - Отступление от ТЗ в сигнатурах: везде первый аргумент — `BrainContext` (тенант, сессия, часы, модели), а не `account_id`. `propose` возвращает принятых кандидатов и сразу записывает знания; `run` отдаёт ещё id затронутых знаний (для сообщений владельцу).
2. **Разбор правки.** Слова без учёта регистра и знаков препинания, `difflib`. Виды: `removed_phrase` (удалённые фразы + `removed_at_start`), `word_replace` (до 3 слов с обеих сторон), `shortening` (текст ≤ 85 % исходного), `casing` (lower / upper / mixed), `restructure` (набор слов тот же ≥ 80 %, порядок похож < 75 %). Пустой набор видов — правка без разницы, не сигнал.
3. **Сигналы.** Правки с непустым разбором и отказы с кодами `not_my_voice`/`sounds_ai` (`VOICE_REJECT_CODES` из 9A; остальные причины в голос не идут). Метки `M1…` сквозные: сначала правки, потом отказы (схема `KnowledgeCandidate` требует метки `M<n>`). Меньше двух сигналов — модель не вызывается и граница прохода не сдвигается: правки ждут следующего прохода.
4. **Кандидаты.** Роль `writer`, промпт `teacher.from_reviews.v1`, схема `ExtractionResult` (9A). Только слои `voice` (класс A) и `humanness` (класс C); остальные отбрасываются кодом. Проверки кодом, не моделью: метки существуют; опора из ≥ 2 разных черновиков; каждая фраза в «…» в `statement` должна встречаться в ≥ 2 опорах (в тексте «до» и — у правки — отсутствовать «после»); для `humanness` фраза в кавычках обязательна (по ней линтер ищет совпадение); `owner.is_suppressed` — похожее удалённое владельцем за 30 дней не предлагается. Судья `sanitize` не вызывается: он оценивает «ремесло», а голос и живость — не ремесло.
5. **Вход в Мозг.** Новое знание: `origin = edits`, `risk_class` A/C, версия 1 с `provenance` (промпт, id ревью), эмбеддинг, затем `merge.nearest/relate/apply_relation` (9A) — «то же» вливается в старшее, противоречие открывает конфликт. `same_as_existing` добавляет доказательства существующему знанию. Доказательства: `fit`, основание `review`, `draft_id` правки, вес 1.0 (уникальность знание × черновик держит индекс 9A). Пересчёт — `scoring.recompute`. Сигнатуры `brain/*` не менялись; из `brain.extract` используются `_embed` и `_passport`.
6. **Класс A (голос).** Остаётся `candidate`, `owner_state = none`: автоматика его не двигает (авто-испытание только для класса B), он виден в `class_a_pending`, и владельцу уходит сообщение «🎙 Заметил: …» (`render_class_a` из 9C) с «Да / Нет / Изменить». «Да» — `owner.confirm`; в обработчике бота сразу после него вызывается `apply_confirmed_voice_item`. Жёсткое правило — знание `anti_pattern` слоя `voice` с фразой в кавычках: фразы добавляются запретами в паспорт, новая версия сразу активная (`style.service.add_banned_phrases_in_session`, в транзакции вызывающего); повтор и уже запрещённое — `None`, версия не создаётся. Остальное знание о голосе паспорт не меняет и идёт в пакет через базу.
7. **Класс C (живость).** Создаётся и сразу переводится в `active` (правило `edits_soft_warn`) — `DbClassCRules` (этап 11) подхватывает его как мягкий запрет: предупреждение линтера. `SoftRule.confirmed` (новое поле, по умолчанию `False`) заполняется из `owner_state ∈ {confirmed, pinned}`; `ClassCRule` тогда даёт `level = error`. Подтверждение — обычное «В работу» из 9C.
8. **Убранные приёмы.** Применённое в черновике знание с детектором: приём «был до и пропал после» (feature — по признакам `compute_features`, rubric — судья 9A). Второй и каждый следующий раз за 30 дней (последние 10 правок знания) — доказательство `fit` с весом 0.5 в минус на черновике этой правки (уникальный индекс не даёт задвоить с `record_from_review`; при сильной переписке минус уже есть, второй не пишется). Первый раз — только запоминается (повторно считается из ревью).
9. **Запуск.** `should_run`: ≥ 5 ревью после последнего прохода (граница — событие `learning.proposed`, новый тип) или есть ≥ 1 новое ревью и проходу (при первом — самому старому ревью) ≥ 7 суток. Задача `learning.propose` стоит в `DEFAULT_SCHEDULES` на 05:30 по поясу аккаунта и проверяет `should_run`; `{"force": true}` пропускает проверку. Запуск «сразу после пятого ревью» ради простоты сводится к суточной проверке — до суток задержки.
10. **Эффект.** `item_effect`: время подтверждения — первое событие `knowledge.owner_decision` (confirm/pin); `zero_edit_rate` = доля `approve` среди решений approve/edit/reject — 20 до и 20 после (первые). `enough` — оба окна полные. Показ пока нигде не подключён (строка недельной сводки — этап 15).
