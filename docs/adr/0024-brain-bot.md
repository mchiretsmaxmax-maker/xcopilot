# ADR-0024: «Мозг» в Telegram (этап 9C)

Статус: принято (ветка `stage/09c-brain-bot`, 15.11.2026). Опирается на ADR-0019 (ядро знаний),
раздел 5.2 `docs/brain-v3.1.md` и ТЗ этапа 9C. Миграции нет.

## Решения
1. **Все решения владельца — `brain/owner.py`, с `ctx` первым аргументом** (как в 9A):
   `confirm`, `confirm_batch`, `reject`, `edit`, `pin`, `disable`, `remove_evidence`,
   `add_manual`, `resolve_conflict`, `set_autonomy`. Каждая проверяет роль `owner` в
   `account_members` (`NotOwner`), меняет базу тем же путём, что автоматика (`lifecycle.apply` с
   `user_id` → actor owner, журнал переходов) и пишет `knowledge.owner_decision` с `ts` от часов
   контекста. Метрика `brain_confirm_load_week` (SQL уже была) считает именно эти события.
2. **«В работу» = переход в `active` + доказательство совместимости** `basis=owner_decision`,
   `dimension=fit`, вес `weights.review.owner_confirm` (3.0). Повтор не дублирует доказательство.
   «Закрепить» = то же + `owner_state=pinned`. «Не моё» = `owner_state=disabled` (знание остаётся,
   в пакет не идёт; в событии `not_mine`). Класс A автоматикой и пакетным «принять» не
   подтверждается никогда — только своим «да» (`confirm`).
3. **«Удалить» — терминальный статус `rejected`.** Автоматика его не трогает (правила `lifecycle`
   на него не смотрят), `confirm` из него — `InvalidItem`. «Не предлагать похожие 30 дней»:
   при удалении вектор знания перезаписывается по `statement`; `owner.is_suppressed` ищет
   близкие (порог `embedding_models.related_threshold`) отклонённые знания за 30 дней, и
   `extract.ingest_candidates` пропускает такие кандидаты до судьи (дешёвый путь, без вызова
   моделей). Без эмбеддера подавление выключено.
4. **Своё знание проходит ту же схему.** `owner.check_text`: утверждение 15–240, указание
   10–200 знаков; без ссылок, хэндлов, тикеров и обращений к модели. `add_manual` создаёт знание
   `thesis / craft / general`, класс B, цель `quality`, `origin=owner`, `active`,
   `owner_state=confirmed`; указание = то же предложение (≤ 200). Слой `voice` из ручного ввода
   не создаётся (голос — только из правок и своих материалов).
5. **Конфликты.** «Первое»/«второе»: связь `resolved`, победителю отменяется переход в
   `conflicted` (`lifecycle.revert`), проигравший — `archived` (правило `owner_conflict`). «Оба»:
   у каждого в области действия появляется `goal = его target_metric`, оба возвращаются из
   `conflicted`, связь `scoped`; если цели совпадают или не из {reach, engagement, replies,
   saves} — `InvalidItem` («развести нечем»).
6. **Сегменты.** Девять сегментов ТЗ уже лежат в `global` (миграция 0005); `ensure_defaults`
   копирует их аккаунту и добавляет четыре сегмента целей (`goal_reach|engagement|replies|saves`).
   Он вызывается при онбординге и при `/brain` (идемпотентно). Списки и счётчики читают
   `v_segment_items`; считаются только рабочие статусы (candidate … conflicted). Сегмент
   «Жанр/Ниша/Язык» отдельными кнопками не показываются (остаются фильтрами в БД).
7. **Недельная сводка — `brain/digest.py`.** `weekly_digest(ctx, week)` — чтение журнала за
   `[week, week+7)` по поясу аккаунта: материалы, новые знания, усилившиеся/ослабшие (системные
   переходы), автоиспытания (с `transition_id`; отменённые не показываются), класс A, открытые
   конфликты, число постов с применёнными знаниями (< 10 — «мало данных»). «Принять всё» =
   `confirm_batch` только по списку автоиспытаний сводки; «Убрать» = `lifecycle.revert`
   (только системные переходы). Задача `brain.weekly_digest` + расписание «понедельник 09:00 по
   поясу аккаунта» в `DEFAULT_SCHEDULES`; пустая неделя не шлётся. Строки «выбрал вариант с
   приёмом в N из M запусков» и «перцентиль вовлечённости» из примера ТЗ не реализованы: нужны
   данные этапов 12–14 (выбор варианта и исходы постов с применёнными знаниями).
8. **Автономия.** `/brain settings`: автоиспытания вкл/выкл, значение — `accounts.settings
   {brain: {autonomy: auto|manual}}` (без миграции). При `manual` `lifecycle.run` пропускает
   правило `auto_probation`. Лимит испытаний в неделю, точечное чтение и «отбор по умолчанию»
   остаются в существующих настройках (`brain.toml`, «Доступ к X») и не дублируются.
9. **Откат.** `/brain undo [ГГГГ-ММ-ДД]` и кнопка «⏪ Откат» (вчера / 7 / 30 дней): предпросмотр
   `rollback.plan` (создано, изменено, доказательства) → «Откатить» → `rollback.execute`; затем
   «Отменить откат» → `rollback.undo`. Время отката — конец выбранного дня по поясу аккаунта.
10. **Онбординг: четвёртый шаг не как состояние до подтверждения.** Аккаунта до «Всё верно» нет,
    а существующие тесты онбординга фиксируют конец диалога на `STUDYING` и пустое состояние.
    Поэтому после создания аккаунта бот шлёт вопрос «Что у тебя точно работает?» с кнопками
    [Написать правила] [Пропустить] (до `STUDYING`, которое остаётся последним сообщением); по
    первой кнопке включается `Onboarding.rules`, каждая строка — `add_manual`. Шаг пропускается и
    простым молчанием.
11. **Данные кнопок** `bn:<действие>[:аргументы]` (≤ 64 байт), роутер `bot/routers/brain.py`
    подключён последним. Читать `/brain` может любой участник аккаунта, менять — только владелец.
12. **Зависимости.** `BotDeps.brain: BrainDeps | None`; `app.build_app` отдаёт боту те же
    `BrainDeps`, что воркеру. Без них роутер строит `BrainDeps` без моделей и эмбеддера
    (правка/добавление работают без вектора).

## Не сделано / оставлено
- `/brain export` и поиск через `brain.api.search` — ждут слияния 9B (договорённость 9B↔9C):
  `/brain search` — собственный `ILIKE` по тексту и указанию (`segments.search`), `/brain export`
  отвечает «появится после 9B».
- `seed.copy_seed_to_account` при онбординге по-прежнему не подключён (вне 9C).
- Нет push-сообщений о знаниях класса A вне `/brain` и сводки: приходят отдельными сообщениями
  при открытии `/brain`; подписчик на `knowledge.candidate_created` — задача этапов 12–13.
