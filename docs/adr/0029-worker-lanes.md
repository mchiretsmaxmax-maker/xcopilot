# ADR 0029 — Две полосы воркера (аудит E, AUD-007)

Статус: принято (16.11.2026). Ветка `fix/worker-lanes`. Миграции нет.

## Проблема

Один `Worker` брал задачи строго по одной. Вызов писателя — до 180 с, с повторами шлюза и починкой ответа — минуты. Всё это время стояли приём материалов (`ingest.process`), разбор, уведомления и `ops.alerts`.

## Решение

1. **Две полосы в одном процессе.** Два экземпляра `Worker` с общей очередью, реестром и хуками (`on_dead`, `on_cancel`). Внутри полосы — по одной задаче, как раньше (правила ADR 0022 и этапа 15 не меняются: `shutdown_grace`, возврат без засчитанной попытки, отмена владельцем).
   - **Медленная** (`kinds=SLOW_KINDS`): `writer.generate`, `writer.topics`, `quality.gate`, `brain.extract`, `learning.propose`, `reports.daily`.
   - **Быстрая** (`exclude_kinds=SLOW_KINDS`): всё остальное, в том числе **неизвестные виды** — так они сразу помечаются `dead` с ошибкой «неизвестный вид задачи».
2. **Фильтр в очереди.** `JobsRepo.claim(..., kinds=None, exclude=False)` добавляет `kind IN (...)` / `kind NOT IN (...)` к выборке `FOR UPDATE SKIP LOCKED`; `JobQueue.claim` пробрасывает. Без фильтра — все виды (старое поведение).
3. **`worker_id`** — `hostname:pid-fast` / `hostname:pid-slow`. `host_prefix` (до последнего `:`) у обеих полос `hostname:`.
4. **`recover()` — один раз на процесс.** Он возвращает задачи всего хоста по префиксу. Если бы каждая полоса делала его при старте, вторая могла бы вернуть в очередь задачу, которую первая уже взяла, — двойное выполнение. Поэтому `serve_app` вызывает `safe_recover()` один раз до запуска полос, а полосы стартуют с `run(stop, recover=False)`. `Worker.run(stop)` по умолчанию по-прежнему делает recover (одиночный воркер, тесты).
5. **`App`.** `App.workers = [быстрая, медленная]`; `App.worker` — быстрая полоса (совместимость). `App.drain(max_jobs)` прогоняет очередь всеми полосами по очереди до пустой (сквозные тесты, eval). В `serve_app` полосы идут через тот же `guarded` (`worker-fast`, `worker-slow`): падение любой останавливает процесс, как раньше.
6. **Пул соединений** (`db/engine.py`, 5 + 5) не менялся: на две полосы с наблюдателем отмены его хватает.

## Правило для новых видов задач

Вид относится к медленной полосе, если его обработчик (прямо или через сервис) зовёт LLM с ролью `Role.WRITER` — это вызовы на минуты. Роли `CHEAP` и `JUDGE`, X API, БД и Telegram — быстрая полоса. Новый медленный вид добавляется в `SLOW_KINDS` (`src/xcopilot/app.py`) и в `tests/integration/test_app_lanes.py::test_slow_kinds_are_writer_kinds`. Если не добавить — вид будет работать в быстрой полосе (корректно, но снова задержит приём материалов).

На 16.11 проверено по коду: `Role.WRITER` зовут `writer/drafts.py`, `writer/topics.py`, `quality/loop.py` (переписчик в `quality.gate`), `brain/extract.py`, `learning/from_reviews.py`, `analytics/analyst.py` (`reports.daily` по понедельникам). `style/extractor.py` тоже зовёт `WRITER`, но из бота, не из задачи. `brain.nightly` (разбор конфликтов) зовёт `JUDGE` — быстрая полоса.

## Тесты

`tests/integration/jobs/test_lanes.py`: фильтр `claim`, быстрая полоса работает, пока медленная занята, остановка во время двух задач возвращает обе без засчитанной попытки, один `recover()` возвращает задачи обеих полос, полоса с `recover=False` не трогает задачу соседней, неизвестный вид — в быстрой полосе и `dead`, отмена владельцем прерывает работающую задачу в каждой полосе (`cancelled`, `on_cancel`). `tests/integration/test_app_lanes.py`: состав `SLOW_KINDS`, сборка двух полос в `build_app`, один `recover` на процесс в `serve_app`.

`test-fix`: `tests/e2e/mvp_stand.py` прогонял очередь через `app.worker.drain` — теперь это только быстрая полоса; стенд зовёт `app.drain`.
