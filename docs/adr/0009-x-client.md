# ADR-0009: X-клиент (этап 6)

Статус: принято (этап 6, 13.11.2026). Развивает [ADR-0004](0004-x-modes.md).

## Контекст
Нужно читать пост по ссылке и свои посты с метриками в режимах `off / owned / paid`,
не пропуская ни одного платного вызова мимо учёта и бюджета, и не иметь методов записи в X.
Ключей X на этапе 6 нет.

## Решения
1. **Слои.** `x/api_v2.py` (`XApiV2`) — тонкий GET-клиент без знания о режимах и деньгах;
   `x/oembed.py` — бесплатное чтение по ссылке; `x/client.py` (`XService`) — выбор источника
   по режиму, бюджет, журнал. Остальной код зависит от `XClient` (Protocol), в тестах — `FakeX`.
2. **Только GET.** В `api_v2.py` нет `.post/.put/.patch/.delete` и строк этих методов — проверяет
   `test_client_has_no_write_methods`. Единственный POST — обмен/обновление токена в `x/auth.py`.
3. **Учёт на каждом HTTP-запросе** через `CallMeter`: `before` — `BudgetGuardLike.check(account_id,
   "x_api", оценка)` до запроса (hard-лимит → `BudgetExceeded`, запрос не уходит); `after` — строка
   в `x_api_calls` (фактическая стоимость, BIGINT микродоллары; ошибки и 429 — со стоимостью 0 и
   событием `x.failed`). `BudgetGuard.record` **не вызывается**: BudgetGuard этапа 4 сам суммирует
   `x_api_calls`, иначе был бы двойной счёт. `xcopilot.llm` не импортируется — только Protocol.
4. **Цены** (`x/cost.py: PRICES`, за ресурс): чужой пост 5 000, профиль 10 000, свой пост 1 000,
   свой профиль (`/2/users/me`) 1 000 — последнее допущение, сверить с биллингом X.
   Оценка до запроса: по id (с учётом дедупликации) или по верхней границе `limit` для ленты.
5. **Суточная дедупликация** (правило X: ресурс оплачивается раз в UTC-день) — `DailyDedup`
   в памяти процесса: в `x_api_calls` нет id ресурсов, схему не меняли. После рестарта
   повторное чтение будет учтено ещё раз — ошибка в безопасную (бо́льшую) сторону.
6. **Маршрутизация.** `off`: всё по ссылке — oEmbed; лента и профили — `XModeError`.
   `owned`: свой пост (хэндл в ссылке = свой) и своя лента — API по цене owned; чужой — oEmbed.
   `paid`: пост — API (5 000), профиль — API (10 000). Пост по ссылке при исчерпанном бюджете
   или сбое API — бесплатный oEmbed (таблица сбоев ТЗ 0.3).
7. **Лимиты частоты.** На 429 — пауза до `x-rate-limit-reset` (+1 с; без заголовка — 60 с),
   не больше 3 повторов. Время и сон — через `Clock` и внедряемый `sleep`.
8. **OAuth 2.0 PKCE**, scope `tweet.read users.read offline.access`. Токены — `secrets.kind=x_oauth`
   (JSON: access, refresh, expires_at, scope), Client ID/Secret — `x_client`; всё через `SecretBox`.
   Обновление: процессная `asyncio.Lock` + `SELECT … FOR UPDATE` строки `x_oauth`, повторная
   проверка срока под блокировкой — одноразовый refresh-токен тратится ровно один раз.
   Отказ X при обновлении → `accounts.settings.x_sync_paused=true`, событие `x.failed`,
   уведомление владельцу через `OwnerNotifier` (Protocol; реализует бот). Успешный обмен кода
   снимает паузу. Тексты ошибок не содержат токенов, кода, verifier и Client Secret.
9. **Длина и Web Intent.** `weighted_len` по twitter-text v3 (ссылка 23, широкие символы и
   эмодзи-последовательности 2, NFC). Больше 280 — intent `None`, бот уходит в режим копирования.
10. **Кассеты** `tests/fixtures/x/cassettes/*.json` собраны по документации X API v2, не записаны с
    живого API. **Перезаписать на настоящих ключах** (live-проверка владельцем, `-m live`).

## Последствия
- Новые репозиторные методы без миграций: `XApiCallsRepo` (`log`, `spent_on_day`),
  `SecretsRepo.get_by_kind_for_update`, `AccountsRepo.update_settings`.
- Синк своей аналитики (этап 14) обязан проверять `settings.x_sync_paused`.
- Сборка `XService` под аккаунт (режим, хэндл, `x_user_id`, `XTokens`) — у потребителя (этапы 7/14).
