# ADR-0010: Бот и онбординг — решения этапа 5

Статус: принято (этап 5). Номер 0010 выбран, чтобы не пересечься с ADR этапов 4 и 6.

## Решения
1. **aiogram 3.31 требует `pydantic<2.14`** → в `pyproject.toml` пин `pydantic>=2.13,<2.14` (ТЗ называло 2.14). Поднять, когда выйдет aiogram с поддержкой 2.14.
2. **Диспетчер.** `build_dispatcher(deps)` собирает новый `Dispatcher` и новые роутеры при каждом вызове (`build_router()` в каждом модуле) — один экземпляр `Router` нельзя подключить к двум диспетчерам (рестарт в тестах). Порядок middleware: дедуп → ошибки → флуд (уровень `update`), затем доступ → аккаунт (уровни `message`/`callback_query`). Команды (`start`, `help`, `cost`, `settings`) подключены раньше шагов онбординга, поэтому работают на любом шаге.
3. **Доступ.** Допускаются пользователи из `users`; `OWNER_TG_IDS` заводятся при первом обращении (`is_admin`). Посторонний получает отказ, в БД ничего не пишется (в том числе событий).
4. **FSM в PostgreSQL.** `PgStorage` пишет в `bot_sessions` под системным аккаунтом `global` (у человека до онбординга нет своего аккаунта, а ключ хранилища аккаунта не знает). Неизвестному пользователю состояние не сохраняется.
5. **Дедуп `update_id`** — в памяти процесса (ограниченный LRU на 10 000). Telegram подтверждает offset следующим `getUpdates`, поэтому дубли после рестарта возможны только для последнего пакета; в БД не пишем (схему не меняем).
6. **Флуд** — скользящее окно по `Clock` (по умолчанию 30 обновлений за 10 с); одно предупреждение за всплеск, дальше молча.
7. **Ошибки.** Пользователь видит «Код ошибки: E…» (`NotFound` E404, `Forbidden` E403, `BudgetExceeded` E402, `InvalidTransition` E409, `ExternalServiceError` E502, `AppError` E400, прочее E500); текст исключения в ответ не попадает, детали — в лог (`bot_error`).
8. **События.** Добавлен `user.action` с `props.action` (`start`, `help`, `cost`, `settings`, `menu.<раздел>`, `onboarding.*`, `settings.*`, `budget.raise|wait`, `cancel`). До онбординга событие пишется в аккаунт `global`; отказ посторонним события не создаёт.
9. **Онбординг.** Данные шагов — в FSM (`niche`, `lang`, `samples`, `competitors`). Хэндл своего аккаунта берётся из первого примера-«ссылки на аккаунт», иначе `user<tg_id>`. На «Всё верно» одной транзакцией: аккаунт, участник `owner`, источники и задачи `ingest.process` (`idempotency_key=ingest:<source_id>`, payload `{"source_id"}`). Источники: свой текст → `own_post/manual` + документ; ссылка на пост → `own_post/oembed`; хэндл → `own_post/x_api`; конкурент → `competitor_post/x_api` с `author_handle`. **Статус `pending` из ТЗ в схеме не существует** (`new/parsed/indexed/failed/excluded`), используется `new`.
10. **Уведомления о бюджете.** `metrics.events.emit` получил подписчиков (`add_listener`): `bot.budget_events` на `budget.warning|exceeded` ставит задачу `bot.notify_budget` в той же транзакции; обработчик `handle_budget_notification` (его подключает воркер) шлёт владельцам сообщение. «Поднять на сегодня» удваивает дневной лимит моделей в `budgets`; возврат к прежнему значению в схеме не предусмотрен (нет срока действия) — владелец меняет лимит в `/settings`. Подписчиков включает `run_polling`.
11. **/cost** только читает `llm_calls` и `x_api_calls` (`UsageRepo`); границы суток и месяца — по часовому поясу аккаунта; без строки в `budgets` лимитом считаются `LLM_DAILY_LIMIT_USD` / `X_DAILY_LIMIT_USD`.
